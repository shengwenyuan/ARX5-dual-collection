# Write Project Plans

把讨论中的共识转换为简洁、可执行、可验收的项目文件。探索阶段不抢先定案；用户明确对齐或批准后再固化正式计划。

## 工作流

1. 检查仓库已有文档、目录约定和用户未提交的修改。
2. 区分当前产物：
   - 已有顶层需求或架构大纲：直接更新原文件，避免复制出第二份事实来源。
   - 已对齐的正式开发、测试或部署计划：写入 `docs/<module>/<plan-name>.md`。
   - 架构与部署类正式文档：优先使用 `docs/architecture/`、`docs/deployment/`。
   - 轻量、临时、排障或会话计划：写入 `plans/<plan-name>.md`。
3. 创建文件前先检查同主题计划，优先更新而不是重复创建。
4. 使用小写 kebab-case 目录和文件名；沿用仓库已有且更明确的命名规范。
5. 主动指出需求矛盾、实现风险和更合适的架构选择，不只整理用户原话。
6. 评估重复工作是否值得做成 MCP、Skill、脚本或 CLI；有明确复用价值时主动提出建议。
7. 实施、部署和验收后按下述生命周期维护文件。

## 正式计划

保持计划短而坚定，至少写清：

- 状态：`draft`、`aligned`、`in-progress`、`implemented` 或 `verified`。
- 目标、范围和明确不做的内容。
- 已冻结决策、约束和模块边界。
- 模块语言、接口、数据契约或部署方式。
- 有顺序的实施步骤。
- 测试方法和可判定的验收条件。
- 部署、迁移或回滚要求；不适用时省略。
- 验收结果区，初始可为空但不得虚构通过结论。

把仍未决定的内容集中写入“开放决策”，不要把猜测写成既定事实。正式计划与顶层架构冲突时先停止落盘并请求对齐。

## 完整性校验

默认不增加 SHA 或其他内容校验，不把校验文件当作通用验收项。

只有遇到不可重建资产、跨机器或网络传输、第三方二进制、固件、模型、正式发布物等真实完整性边界时，才在正式计划中主动提出。计划必须先对齐校验对象、生成与验证时机；未对齐前不得擅自增加。

## 实施记录

每轮开发或部署完成后覆盖 `plans/last_edit.md`。该文件只描述最近一轮，不承担长期 Changelog 职责，并保持压缩：

```markdown
# Last Edit

- Plan: 相对路径
- Status: implemented | verified | blocked
- Changed: 本轮实际修改
- Validation: 已执行检查及结果
- Deployment: 部署目标及结果；未部署则写未部署
- Remaining: 尚未完成或已知偏差
```

计划讨论、纯分析和未产生实现变化的工作不得更新 `last_edit.md`。

## 验收回写

完成测试验收后：

1. 更新原正式计划的状态为 `verified`；未全部通过时保持真实状态。
2. 在原计划的验收结果区记录日期、环境、关键检查、结论和偏差。
3. 同步覆盖 `plans/last_edit.md`，使其反映本次验收。
4. 不删除原计划中的决策、未完成项或失败记录。

## 约束

- 保留用户已有修改，不覆盖无关文档。
- 不在 `docs/` 下再创建通用 `plans/` 中间层。
- 不因临时讨论创建正式计划。
- 不把计划写成逐行编码说明；只保留约束开发行为的信息。
- 不将“已实现”和“已验收”混为同一状态。
- 不为了展示完整性而过度建设工具；MCP、Skill 和脚本都必须服务于明确的重复需求。
